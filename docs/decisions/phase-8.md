# Phase 8 — Decisions Log

Making the data and infrastructure layers **survive real infrastructure**. The
core was already correct in memory — exactly-once ledger, PEL/reclaim, idempotent
ingest — but the edges assumed everything stayed up and unchanged: the schema was
conjured by `create_all` with no migration history, a shared SQLite file would
deadlock the API against the worker, a dead Redis surfaced as a `500`, and a hung
Groq call could pin a worker forever. This phase closes those, and it does so at
the **stated scale** — a single-operator showcase serving ~1–50 requests — which
is why one headline item from the original plan (a gunicorn worker farm) was
deliberately *not* built. Each entry: what was chosen, the rejected alternative,
and why.

The through-line: **make the failure modes explicit and bounded.** A migration
is a schema change you can name and reverse; a WAL pragma is a documented
contention policy; a socket timeout is a promise that a dead dependency fails in
seconds, not never; a `503` is an honest "retry me." Nothing here adds a moving
part the scale doesn't require.

---

## 1. Schema is owned by **Alembic migrations**, autogenerated baseline — `create_all` demoted to the test path

**Chosen.** `alembic.ini` + `alembic/` with a single autogenerated baseline
revision (`…_baseline_schema.py`) that creates `pr_jobs`, `review_decisions`, and
`job_results` with their constraints. The container runs `alembic upgrade head`
as a release step before serving. `Base.metadata.create_all` stays in the app
lifespan, but it is now a belt-and-suspenders idempotent no-op in production
(the tables already exist post-migration) and the *primary* schema path only for
SQLite and the in-memory test engine.

**Why.** `create_all` can only ever create what is missing; it cannot alter a
column, backfill data, or record what version a database is at. The moment the
schema needs its first change, a `create_all`-only system has no answer that
isn't a manual `ALTER` run by hand against production. Alembic makes every schema
change a reviewed, versioned, reversible artifact in git — which is the baseline
claim of a system that stores data it cares about. Autogenerating the baseline
(rather than hand-writing it) guarantees the migration and the ORM models agree
on day one; the round-trip CI job (Decision 8) keeps them honest thereafter.

**Rejected — keep `create_all` only.** Fine until the first migration, then
indefensible; "how do you evolve the schema?" has no good answer. **Rejected —
hand-write the baseline.** More error-prone than autogenerate for a schema this
size, and it invites silent drift between the DDL and the models. **Rejected —
drop `create_all` entirely.** Then a `git clone && pytest` must run Alembic before
any test can touch the DB; keeping `create_all` for the in-memory SQLite fixture
preserves the zero-config, no-migration test path while production goes through
migrations.

## 2. The migration URL has **one source of truth**: `settings`, not `alembic.ini`

**Chosen.** `alembic/env.py` pulls the database URL from
`app.config.settings.database_url` and deletes any reliance on `sqlalchemy.url`
in `alembic.ini`. `render_as_batch` is switched on for SQLite; `compare_type`
and `compare_server_default` are on so autogenerate notices column-level drift.

**Why.** Two places that both name the database are two places that drift. Wiring
`env.py` to the same `settings` the app uses means `AUTOPR_DATABASE_URL` governs
the app, the worker, *and* migrations from one env var — the container migrates
exactly the database it then serves. Batch mode is not cosmetic: SQLite cannot
`ALTER TABLE` in place for most changes, so without `render_as_batch` a future
migration that alters a column would apply on Postgres and fail on SQLite; turning
it on now means migrations are portable across both backends the project targets.

**Rejected — the stock `alembic.ini` `sqlalchemy.url`.** A second copy of the
connection string that CI, Compose, and the developer's shell would all have to
keep in sync with `settings` — the exact drift this avoids.

## 3. SQLite runs in **WAL** with tuned pragmas, applied per connection

**Chosen.** `app/db.py` installs a `connect` event listener on the engine for
SQLite URLs that issues `PRAGMA journal_mode=WAL; busy_timeout=5000;
synchronous=NORMAL` on every new connection. Tested in `test_reliability.py`
against a file-backed DB (WAL confirmed) and an in-memory DB (correctly a no-op).

**Why.** The API process and the worker process both open the same SQLite file in
local/dev runs. Under the default rollback journal, a writer takes a lock that
blocks all readers, so the two processes trip over each other with "database is
locked." WAL lets readers and the single writer proceed concurrently, which is
the actual local topology. `busy_timeout=5000` turns a millisecond-long lock
collision into a short wait instead of an instant error, and `synchronous=NORMAL`
is the documented, recommended durability point under WAL — crash-safe for the
application, without an `fsync` on every commit. The pragmas are per-connection
(SQLite scopes them to the connection), so the listener must run on *every*
connect, not once at startup — hence the event hook rather than a one-shot.

**Rejected — leave SQLite at defaults.** Reproduces the "database is locked"
class of bug the moment the worker and API share a file. **Rejected — set the
pragmas once at startup.** Wrong mental model: a new pooled connection would come
up at the defaults. **Rejected — only do this for Postgres deployments and ignore
SQLite locking.** SQLite *is* the local and demo story; leaving it fragile
undercuts the "clone and run" path.

## 4. `PRAGMA foreign_keys=ON` was **deliberately not** enabled

**Chosen.** The pragma set is WAL + busy_timeout + synchronous only. SQLite's
foreign-key enforcement stays at its (off) default.

**Why.** This is an honest, flagged trade. Enabling FK enforcement mid-project
turned several existing tests red: fixtures that insert a `job_results` row or a
child record without first materializing the exact parent relied on SQLite *not*
enforcing the constraint (Postgres, which enforces natively, is exercised by the
integration path). Turning it on would have meant reworking those fixtures for a
guarantee the production database (Postgres) already provides. At this scale the
proportionate choice is to keep the 180+ existing tests green and rely on
Postgres for real referential integrity, rather than harden SQLite to a standard
its role (local/dev/test) does not require. Documented here so it is a decision,
not an oversight.

**Rejected — turn it on and fix the fixtures.** Real work for a property the
production engine already enforces; deferred as not worth the churn at this scale.

## 5. The Redis client is built with **timeouts and health checks**, not bare defaults

**Chosen.** `make_client` (`app/queue.py`) sets `socket_timeout`,
`socket_connect_timeout`, `health_check_interval`, and `retry_on_timeout=True`
from settings. A regression test asserts all four land on the connection pool.

**Why.** redis-py's defaults are "wait forever." With no `socket_connect_timeout`,
a Redis that is down (not refusing — *black-holed*, e.g. a dropped network) makes
the webhook handler hang until the OS TCP timeout, tens of seconds later — the
worst failure mode, because it consumes the request slot and looks like a hang,
not an error. Bounding connect and socket time means a dead dependency fails in
seconds. `health_check_interval` pings a pooled connection that has been idle, so
a connection that went stale (Redis restarted under us) is detected and replaced
rather than surfacing as a spurious mid-request error. `retry_on_timeout` absorbs
a single transient blip without bubbling it to the caller. These are the settings
that separate "degrades predictably" from "hangs mysteriously."

**Rejected — bare `from_url`.** The unbounded-wait default; the hang-on-dead-Redis
behavior above is exactly what it produces.

## 6. A runtime queue outage on publish is a **503, and the job row survives**

**Chosen.** `ingest` commits the `PRJob` row as `PENDING` *before* it calls
`queue.publish`. The `/webhook` handler wraps the `ingest` call in
`except RedisError` → **503** with a `queue temporarily unavailable` body (it was
an unhandled `500` before). Two tests cover it: the status is `503`, and a
single `PENDING` row remains afterward.

**Why.** The status code is a contract with GitHub's delivery system. A `500`
reads as "permanent server bug" — GitHub logs a failed delivery and moves on, and
the event is lost. A `503` reads as "temporarily unavailable, retry" — which is
the truth when Redis is briefly down, and GitHub *will* redeliver. Pairing that
with committing the row *before* publish makes the outage fully recoverable
without relying on redelivery at all: the worker's startup reconcile scans for
`PENDING` jobs and re-enqueues them, so even a webhook that never gets retried is
picked up. The row-before-publish ordering is what makes the `503` honest rather
than a promise the system can't keep.

**Rejected — let it 500.** Turns a transient, recoverable outage into a dropped
event. **Rejected — publish inside the same transaction / before the commit.**
Then a publish failure would roll back the row and the reconcile safety net has
nothing to find; the event really is lost. The ordering is load-bearing.

## 7. The LLM call is **time-bounded** with `request_timeout`

**Chosen.** `get_llm` builds `ChatGroq` with
`request_timeout=settings.llm_timeout_s` (30s default), alongside the existing
`max_retries`. A test constructs the client (with a dummy key, no network) and
asserts the timeout is set.

**Why.** The worker processes one job to completion; an LLM call with no timeout
can hang on a stalled connection and pin that worker indefinitely, silently
halting the pipeline with no error to alert on. A bounded `request_timeout`
converts "hung forever" into a clean, retryable failure the existing tenacity
retry and the job's bounded-attempts→DEAD machinery already know how to handle.
It is one field, and it closes the last unbounded wait on the hot path.

**Rejected — no timeout.** The silent-hang failure mode above. **Rejected — a
short aggressive timeout.** The 70B model's legitimately long responses would be
cut off; 30s is comfortably above normal completion and still bounds the pathology.

## 8. Compose migrates **once** (api only) and CI proves the migration on **real Postgres** — but the unit suite stays hermetic

**Chosen.** In `docker-compose.yml` only the `api` service runs
`alembic upgrade head` (as `sh -c "alembic upgrade head && uvicorn …"`); the
`worker` waits on `api: condition: service_healthy` so exactly one process
migrates and the worker's `create_all` is a no-op against the already-migrated
schema. The `api` healthcheck probes `/healthz` with the stdlib (no `curl` in the
slim image). A dedicated CI job (`migrations`) brings up a real Postgres service
and drives the schema **up → down → up**. The unit suite itself remains fully
offline (in-memory SQLite + fakeredis).

**Why.** Two processes racing `alembic upgrade head` against one database is a
real hazard (concurrent DDL, duplicate version rows); gating the worker on the
api's health makes migration a single-owner release step, which is the standard
pattern. The CI split reflects where each kind of confidence actually comes from:
the unit suite's value is that it is fast and hermetic, so it must not depend on
live infrastructure — but hermeticity means it never exercises *Postgres* DDL or
the reversibility of a `downgrade()`. The `up → down → up` round-trip on real
Postgres covers exactly that gap: it proves the generated migration is valid
Postgres, that every downgrade is real, and that re-upgrading is clean. Running
the SQLite-based suite "against" a Postgres service it overrides in `conftest`
would be theater; the round-trip is the honest integration test for this layer.

**Rejected — both api and worker migrate.** The concurrent-DDL race above.
**Rejected — a separate one-shot `migrate` service/container.** Cleaner in a
large deployment, but at this scale it is a third service to define and sequence
for what a `depends_on: service_healthy` edge already gives; deferred with the
scale-out notes. **Rejected — run the whole suite against real Postgres+Redis in
CI.** The suite is deliberately hermetic (`conftest` hardwires SQLite + fakeredis
for speed and determinism); reworking it to target live backends is a large change
whose unique yield over the round-trip job — real Postgres DDL validation — is
already captured by that job. Flagged as a corner below.

## Corners cut (flagged, deferred)

1. **Single `uvicorn` process — no gunicorn worker farm.** The original Phase 8
   plan named `gunicorn -k uvicorn.workers.UvicornWorker -w 2`. It was
   deliberately *not* built: at the stated 1–50-request, single-operator scale a
   multi-worker farm is weight without benefit — more moving parts, a shared-state
   story to reason about (the in-process rate limiter from Phase 7 would fragment
   across workers), and nothing to justify it under the actual load. One uvicorn
   process is the proportionate choice. The scale-out path (multiple workers /
   replicas behind a shared Redis for limiter state) is real and noted; it belongs
   to a horizontal-scaling phase, not this one. This is a considered deviation
   from the plan, in line with the "not heavy — normal, working" scope direction.

2. **The unit suite does not run against real Postgres/Redis.** By design it is
   hermetic (SQLite + fakeredis). The `migrations` CI job covers real-Postgres DDL
   and downgrade reversibility, but the *behavioral* suite (idempotency, reclaim,
   routing) runs only on the offline backends. Fidelity caveats are already
   documented in `conftest.py`; a full real-backend behavioral job is deferred as
   low marginal yield at this scale.

3. **No hard token/size cap on LLM inputs.** The plan mentioned one alongside the
   timeout. Inputs are bounded in practice by the PR-diff reader's own truncation
   upstream, and the `request_timeout` now bounds the call's wall-clock regardless
   of input size, so the acute failure mode (unbounded wait) is closed. An
   explicit token-count cap in `get_llm`'s callers — belt to the reader's
   suspenders, and a guard against a pathologically large single hunk — is
   deferred, with `app/agents/llm.py` the place it would live.

4. **`create_all` still runs in the app lifespan.** After the migration release
   step it is a redundant no-op in production. It is kept intentionally (it is the
   schema path for the in-memory test engine and a first-run SQLite file), but a
   reader should know the production schema is owned by Alembic, and the lifespan
   `create_all` is a convenience that happens to be harmless there — not the
   source of truth.

5. **The `api` healthcheck probes `/healthz` (liveness), not readiness.** A deep
   `/readyz` that checks DB + Redis reachability is a **Phase 9** deliverable;
   until it exists, Compose's healthcheck confirms the process is up and serving,
   which is enough to gate the worker's start. The healthcheck graduates to
   `/readyz` when that endpoint lands.

6. **`downgrade()` to base drops tables — it does not preserve data.** The baseline
   migration's downgrade is the honest inverse of "create everything": it drops
   the tables. That is correct for a baseline and is what the CI round-trip
   exercises, but it means `downgrade base` on a populated database is
   destructive. Real data-preserving down-migrations become relevant only once a
   migration alters populated tables; noted so the round-trip's `downgrade` is not
   mistaken for a backup-safe operation.
